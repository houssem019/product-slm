# Build Log

Chronological record of what was built, **why**, and which alternatives were rejected.
Read this before an interview to retell the story of the project.

| Step | What | Why / alternatives considered |
|------|------|-------------------------------|
| 1. Schema | `src/pslm/schema.py`: Pydantic `ProductAttributes(category, brand, size, material)`. Brand, size and material are nullable. `category` is a closed `StrEnum` of 23 top-level classes. `extra="forbid"`. | **One schema serves teacher, student, guided decoding and eval**, so "valid output" means the same thing at every stage. **Closed category set:** free-text categories make exact match meaningless ("Kitchen" vs "Home & Kitchen") and let the student invent labels. Amazon's own `main_category` was rejected: it's null for ~25% of rows and often wrong (a "baby decision coin" filed under Office Products). |
| 2. Labeling guidelines | `docs/LABELING.md`: title-only, copy brand/size verbatim, conservative nulls, many explicit edge-case rules. | **Distillation quality is capped by label consistency.** Without rules, the same teacher labels "Wooden" one time and "wood" the next, and the student learns noise. **Verbatim spans make labels checkable:** a brand or size not found in the title is a guaranteed error. Rules were added *while labeling the test set*, as real ambiguities came up (vacuums, plated jewelry, compatibility sizes). That's normal annotation-guideline iteration. |
| 3. Data source | Amazon Products 2023 (`milistu/AMAZON-Products-2023` on HF, 117k products, derived from McAuley-Lab Amazon Reviews 2023). DuckDB reads three columns from the remote parquet; the cache in `data/raw/` is 9.8 MB. | **Real, noisy marketplace titles:** keyword stuffing, compatibility lists, mixed units. That's exactly the target domain. The dataset is ~1.7 GB because of precomputed embeddings, but **parquet column projection over HTTP** pulls only what we need. Rejected: WDC product corpus (huge, multilingual, needs heavy filtering); the full McAuley meta dumps (tens of GB). |
| 4. Sampling | `pslm.data.sample`: dedupe on lowercased title; ASCII-only, 15–220 chars; deterministic hash order (`hash(id ‖ seed)`); no source category above 20% of the sample. Splits: 150 test / 50 val / 600 train, committed as JSONL. | **The cap stops the sample being mostly Amazon Home** (~35% of the source). **Hash order is a reproducible shuffle without RNG state.** Test is taken first, so growing train later never leaks a test title. **Committed splits** pin labels to exact titles, and CI needs no network. |
| 5. Labels (teacher) | All 800 titles labeled by **Claude (Opus 5.5) inside the Claude Code session**, following LABELING.md. Written as compact TSV, imported to `data/labels/<split>.jsonl` with `labeler` provenance and a `reviewed` flag. | **No API key on this machine**, and the plan budgets ~$0. An in-session teacher is the same model family a Batch API job would use, at no cost. An API batch labeler (`distill/`) is still planned for scaling to 5–10k titles. **TSV** keeps hand/LLM writing compact (5 fields per line); **JSONL** is the source of truth. |
| 6. Automated label QA | `pslm.data.labels check`: schema validity, id/title alignment, and **grounding**: brand and size must appear in the title (case- and space-insensitive). All 800 pass. | **A cheap check that catches hallucinated attributes**, the most common LLM-labeling error. It runs as a pytest on the committed labels, so a bad edit fails CI. It can't check category or material semantics; that's what human review is for. |
| 7. Human review tool | `pslm.data.review test`: Enter = accept, `e` = edit per field with validation, saves after every record. Keeps the teacher's original under `teacher_label`. | **The test set is gold only after a human pass**, otherwise we'd be measuring agreement with the teacher, not accuracy. Keeping `teacher_label` lets us report the **teacher's own per-field error rate**, which bounds what distillation can achieve. |
| 8. Pluggable LLM layer | `pslm.llm`: one `complete(system, user, json_schema)` interface. Providers: `anthropic` (official SDK), `ollama` (local), `fake` (cassette replay), plus `ScriptedLLM` for unit tests. | Same pattern as the sibling repos. **CI and tests never need a key or network.** Rejected: LangChain/LiteLLM wrappers. One call shape doesn't need a framework, and the abstraction would hide the provider features we rely on (structured outputs, caching, fallbacks). |
| 9. Constrained JSON everywhere | `output_schema()`: a flat hand-written JSON schema used by Claude structured outputs (`output_config.format`), Ollama `format`, and later vLLM guided decoding. One `parse_output` reports `not_json`/`invalid_schema`/`refusal`/`truncated`. | **JSON validity should come from decoding, not from hoping.** A shared parser means "valid" is defined once for teacher, baselines and student. Rejected: Pydantic's generated schema (`$defs`, `anyOf`: CHALLENGES #6); tool-use-as-JSON (structured outputs is the direct feature). |
| 10. Two prompts | `teacher_system()` = the full `docs/LABELING.md` + 4 train-only worked examples (~1.5k tokens, cached). `STUDENT_SYSTEM` = one line + the category list. | The teacher needs the rules; the student learns them from data, and short prompts mean shorter training sequences and faster inference. The guideline doc is **embedded at runtime**, not copied, so there's one source of truth, and editing it invalidates cassettes (by design). |
| 11. Sync labeler / baseline runner | `pslm.distill.label <split> --provider ...`: predicts, writes `data/preds/<split>/<model>.jsonl`, and scores against the reference labels. Also reports strict JSON rate, latency p50/p95 and cost per 1k titles. | One runner for "label with the teacher" and "zero-shot baseline". The baseline comparison table later reuses exactly this output. |
| 12. Batch API teacher | `pslm.distill.batch estimate|submit|collect`: same `request_params` as sync (minus refusal fallbacks, which batches reject). `custom_id` = product id; results are re-ordered by id. | **50% cheaper and asynchronous**, the right tool for one-off bulk labeling. `estimate` gives offline cost: 600 titles cost ~$1.6 on Opus 5.5 and ~$0.04 on Haiku 5.5. Implemented and unit-tested with fake result objects. **Not run: no API key** on this machine; the committed labels come from the in-session teacher. |
| 13. Metrics | `pslm.eval.metrics.score`: per-field accuracy; extraction P/R/F1 for brand/size/material; all-fields exact match; per-category accuracy; invalid-output breakdown. | Accuracy alone flatters a model that always says null (~74% of titles have no size). P/R/F1 with non-null as the positive class shows whether it actually extracts. An undefined F1 is `None`, not 0 (CHALLENGES #7). |
| 14. Test-set review | A second pass over all 150 test labels against the guidelines. 2 edits: #146 size `32x64in` → `Large` ("Large Size" comes first); #61 brand "Emily the Strange" → null (licensed character). Both originals are kept as `teacher_label`. A scan of train/val for the same patterns found **an ambiguity, not more errors**: "Small Travel Umbrella" uses Small as an adjective. So `docs/LABELING.md` now defines when Small/Large is a size designation. | The user delegated the review to me. **Caveat: the reviewer is the same model that labeled.** It catches rule slips, not systematic blind spots. Every record says `reviewer: "claude-opus-5-5 (second pass, same model as the labeler)"`, and the README doesn't call the test set human-reviewed. The guideline edit changed the teacher prompt hash, so the qwen baseline was **re-recorded**: exact 0.40 → 0.46, with only that one sentence changed. That's within n=50 noise, but it's also a measurement of zero-shot prompt sensitivity. |
| 15. SFT data | `pslm.train.format` writes `data/sft/{train,val}.jsonl`: (`STUDENT_SYSTEM`, `Title: ...`, canonical JSON). The canonical JSON has a fixed key order, `, `/`: ` separators and explicit nulls. `build("test")` raises. | **One target string per title:** if `{"brand":..}` and `{"brand": ..}` were both acceptable, the loss would be spent learning formatting variance. The test split never reaches training code, and a test enforces that. |
| 16. Trainer | `pslm.train.train`: plain HF `Trainer` + a 20-line collator. **Loss on assistant tokens only**; the prompt is masked to -100. LoRA r=16/α=32/dropout 0.05 on all 7 attention+MLP projections. `--load-in-4bit` = QLoRA (NF4, double quant, fp16 compute, k-bit prep + gradient checkpointing). 3 epochs, lr 2e-4 cosine, effective batch 16. | **Masking:** the ~150-token prompt is identical boilerplate. Unmasked, it would dominate the loss on 600 examples. A test decodes the unmasked tokens with the real Qwen2.5 template and asserts they equal exactly the JSON + `<|im_end|>`, so the model also learns to stop. **All-linear LoRA:** adapting only q/v underfits format-heavy tasks on small models. **Not TRL:** its SFT API has churned across versions; the explicit collator is easier to verify and to explain. **transformers 5:** `warmup_ratio` is gone, so the 5% warmup is computed into `warmup_steps`. Max sequence is 278 tokens (mean 179), so `max_len=384` never truncates, and an over-long example raises instead of being cut silently. |
| 17. Base model | **Qwen2.5-1.5B-Instruct** for the T4 run; the tiny `trl-internal-testing/tiny-Qwen2ForCausalLM-2.5` for smoke tests. | It's Apache-2.0 and not gated (Llama 3.2 needs a license click-through on every machine, including Colab), and PEFT, bitsandbytes and vLLM support it well. Qwen3 was rejected because of its default thinking mode: extra chat-template handling for no gain on a 40-token JSON task. The tiny model has random weights but the real tokenizer and template, so the smoke test exercises exactly the masking path. |
| 18. HF inference provider | `pslm.llm.hf_client.HFLLM`: loads base + adapter, merges the LoRA, decodes greedily with **no constraints**, `max_new_tokens=96`. Registered as `--provider hf` in the same runner, so it gets the same metrics, prediction files and cassettes. | **One runner for every model** makes the comparison table apples-to-apples. Unconstrained decoding here measures the student's own JSON validity; guided decoding is a serving-time guarantee (vLLM, next milestone). The **zero-shot base with the same short prompt** is also run, which isolates what fine-tuning added. |
| 19. Colab notebook | `notebooks/train_colab.ipynb` (linted and formatted by ruff like the rest of the code): clone → install `[train]` + bitsandbytes → format → QLoRA → eval fine-tuned and zero-shot on val+test with `--record` → zip the preds, cassettes, summary and adapter. | **There's no local NVIDIA GPU.** A free T4 is the target. Recording cassettes on Colab means CI can replay the GPU model's outputs on a CPU runner. |
| 20. T4 training run | The owner ran `notebooks/train_colab.ipynb` on a Colab T4. It needed two notebook fixes first: the Python 3.13 cap and a stale preinstalled torchao (CHALLENGES #11, #12). QLoRA on Qwen2.5-1.5B-Instruct took **447 s**, training 18.5M of 1.56B params (1.2%). Train loss 0.40 → 0.010; val loss 0.0536 / **0.0477** / 0.0493 by epoch. | Training cost: free. Every fix went into the notebook and the repo, so a clean "Run all" now works top to bottom. Epoch 3 slightly overfit (CHALLENGES #14). That's documented, and I didn't re-tune on test. |
| 21. Student evaluation | The same runner, metrics and cassettes as every other model: fine-tuned and zero-shot 1.5B on val+test, recorded on the T4, replayed offline with identical numbers. qwen2.5:7b re-run on the 150 test titles (local CPU) for a same-data comparison. Error analysis: CHALLENGES #13. | **The zero-shot 1.5B with the same short prompt is the control.** It isolates the adapter's contribution from the base model's ability. The 7b row answers "why not just prompt a bigger model?" |
| 22. Eval regression gate | `pslm.eval.gate` + `data/eval/baseline.json`: per-run, per-split minimums (measured − 0.02, rounded down) for exact match, JSON validity, per-field accuracy and F1. `pslm.distill.label --gate` exits 1 below any of them. CI replays the fine-tuned cassettes through the gate on 3.11 and 3.13, and uploads the replayed predictions as an artifact. A test checks the committed baseline passes against the committed reports. | **What a replay gate can and can't catch:** it re-grades fixed outputs, so it catches regressions in parsing, normalization, metrics or gold labels, and a prompt change fails earlier as a cassette miss. A *new model* means re-recording on a GPU and moving the baseline in the same commit, so the change is reviewed rather than silent. The −0.02 slack lets a one-label correction through without a baseline edit. An undefined F1 (`None`) fails the gate rather than silently passing. |
| 23. Significance check | `pslm.eval.compare A B --split test`: per-metric difference with a 95% **paired** bootstrap CI (10k resamples, seed 0), plus the count of titles only A or only B got right. Results: fine-tuned vs zero-shot 1.5B exact +0.527 [+0.447, +0.607]; fine-tuned vs qwen2.5:7b exact +0.067 [−0.027, +0.160], brand −0.047 [−0.107, +0.007], so **not significant**. | On val (n=50) the student looked clearly better than the 7b (0.64 vs 0.46). On test the gap shrank, and the 7b leads on brand. I ran the check *before* writing a claim, and the README now says "matches", not "beats". Paired resampling is the right test, because both models see the same titles, and per-title difficulty is shared. |
| 24. Serving backends | `pslm.serve.backends`: one `extract(titles) -> BatchResult` interface. **`vllm`**: base + LoRA via `LoRARequest`, `StructuredOutputsParams(json=output_schema())`, greedy, fp16, `max_model_len=512`; the whole request goes in one `generate`. **`hf`**: CPU fallback. **`replay`**: the fine-tuned model's cassette, indexed by title. Same chat-template prompt and same `parse_output` everywhere. | **Serving must not drift from eval.** A test sends all 150 test titles through the HTTP API (replay backend) and asserts the served attributes equal the evaluated predictions title for title. vLLM API checked against current docs: `guided_*` was removed in v0.12; it's `structured_outputs` now. Prompts are rendered with the tokenizer's chat template and sent to `llm.generate`, the same string the HF path builds, rather than `llm.chat`, whose LoRA support the docs don't state. |
| 25. API | `pslm.serve.api`: FastAPI `POST /extract {"titles": [...]}` (1–256 titles, each ≤500 chars, whitespace squashed). The response is per-title `attributes` or `error`, in order; one bad title never fails the batch. `GET /health` (503 until loaded), `GET /metrics` (requests, titles, errors by type, batch and per-title latency p50/p95, titles/s of backend time). `create_app(backend)` injection for tests; the backend lock serializes requests. | **Batch per request, lock across requests:** vLLM's offline `LLM` isn't thread-safe, and FastAPI runs sync endpoints in a thread pool. Rejected for now: vLLM's `AsyncLLMEngine`/OpenAI server behind the API, which batches *across* concurrent requests. That's the at-scale answer, but it's a separate process to operate, and in-request batching already captures most of the GPU efficiency for a bulk-enrichment API. |
| 26. Benchmark | `pslm.serve.bench`: titles/s, batch latency p50/p95 and ms/title at batch sizes 1/8/32/150 (warm-up excluded), plus accuracy of exactly what the backend serves, written as normal prediction rows (`qwen2.5-1.5b-lora-<run>`) so `compare` and the gate apply. `notebooks/serve_bench_colab.ipynb` runs vLLM guided, vLLM unguided and HF sequential on a T4. | **Throughput and accuracy measured together:** a faster config that changes outputs (guided vs unguided decoding) has to show its accuracy too. The adapter is uploaded as a zip, so the owner doesn't need a Hugging Face account or a retrain. |
| 27. Docker | `Dockerfile` (CPU): python:3.12-slim + uv 0.13.1, `uv sync --locked --no-dev`, layer-cached deps, non-root user, HEALTHCHECK on `/health`, replay backend by default. `WITH_HF=1` adds CPU-only torch from the PyTorch index. `Dockerfile.gpu`: `vllm/vllm-openai:v0.31.0` + this package, adapter mounted at `/models/adapter`, entrypoint replaced with our API. | **CI builds the CPU image and smoke-tests it:** it waits for a healthy container, then checks `/extract` for a recorded title and an unrecorded one, plus `/metrics`. CPU torch comes from the PyTorch index because PyPI's Linux wheel pulls ~3 GB of CUDA libraries. vLLM v0.31.0 is the newest release that's 2+ weeks old (v0.32.0 was 3 days old). The GPU image isn't built in CI: no GPU runners, and the image is ~10 GB. |

## First baseline: zero-shot qwen2.5:7b (Ollama, CPU), val split

These are measured on the 50 **val** titles against the in-session teacher labels. The prompt is the teacher prompt with Ollama's schema-constrained decoding. `data/preds/val/qwen2.5-7b.report.json` has the full numbers, and CI replays it from `data/cassettes/qwen2.5-7b.json`.

| metric | value |
|---|---|
| JSON valid (lenient / strict) | 1.00 / 1.00 (constrained decoding) |
| exact match (all 4 fields) | 0.46 (0.40 before the step-14 guideline clarification; see below) |
| category accuracy | 0.68 |
| brand acc / F1 | 0.88 / 0.889 |
| size acc / F1 | 0.80 / 0.571 (precision 0.47) |
| material acc / F1 | 0.90 / 0.696 |
| latency p50 | 10.6 s per title (CPU, 1.7k-token prompt) |

**Error analysis:** most misses break a written rule the model was given.
- **Category:**
  - shoes labeled `apparel` (3 of 4 footwear titles);
  - furniture labeled `home_kitchen`;
  - sunglasses labeled `apparel`.
- **Size:**
  - pack counts ("3-Pack", "28 Strips", "140 tablets");
  - the compatible phone's screen size;
  - named sizes like "Small"/"Preseason".
- **Material:** fabric specs like "600D" were taken as the material.
- **Brand:** one hallucinated brand ("Dannxe" for "Danxee"), the failure the grounding check exists for.

Rule-following on a fixed domain is exactly what fine-tuning teaches, so this is the bar for the student to beat. Caveat: n = 50, so ±0.07 on any rate is noise.
